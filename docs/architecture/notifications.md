# Notification Service

Stores and serves in-app notifications for students, tutors, and admins. Other services call this service to notify users. The dashboard calls it to display them.

The calling service works out who the notifications go to(for example, which tutors are subscribed to a topic) and passes in the list of recipients.


## Architecture

```
Calling service (requests, bookings, lessons)
        |  POST /notifications  (recipient_ids, type, actor_id, link, ...)
        v
   API layer (Flask blueprint)  -- API key check, request validation
        v
   NotificationService.send()   -- validates type, recipients, link
        v
   NotificationStore (interface)
        v
   MongoNotificationDAO         -- MongoDB "notifications" collection
        ^
        |  GET inbox / unread-count / mark read
   Dashboard service (student, tutor, admin)
```

- Notifications and read/unread state are independent per person.
- A `NotificationChannel` interface will be added when email, push, or a third-party provider is integrated.
- Notifications carry a `link`, but this service does not guard it. The service that owns the destination page checks permissions.

## Notification document

| Field | Type | Notes |
|---|---|---|
| `id` | string | Generated by the service |
| `recipient_id` | string | Who receives it. Must use the same user ID format as the rest of the platform |
| `actor_id` | string or null | The user who caused it. `null` for system-generated ones (e.g. reminders) |
| `type` | string | One of the values in the enum below |
| `title` | string | Short headline |
| `body` | string | Optional longer text |
| `link` | string or null | Relative path the UI opens on click, e.g. `/requests/abc123` |
| `payload` | object | Extra data, e.g. `{"request_id": "abc123"}` |
| `read_at` | ISO datetime or null | `null` means unread |
| `created_at` | ISO datetime | UTC |

### Notification types

Values must match the `NotificationType` enum exactly.

| Type | Typical actor | Typical recipient |
|---|---|---|
| `request_canceled` | The user who canceled | The other party |
| `booking_created` | The user who booked | The other party |
| `lesson_reminder` | none (system) | Everyone in the lesson |



All requests need the service API key header (see Auth)

### Send a notification

`POST /notifications`

```json
{
  "recipient_ids": ["tutor_7", "tutor_12"],
  "type": "request_canceled",
  "actor_id": "student_42",
  "title": "Lesson request canceled",
  "body": "Sarah canceled her Calculus request.",
  "link": "/requests/abc123",
  "payload": {"request_id": "abc123"}
}
```

Response `201`: the list of created notifications (one per recipient).

- `recipient_ids` must be non-empty. Duplicates are removed.
- `type` must be a valid enum value, or the request fails with `400`.
- `link`, if present, must start with a single `/` (not `//`, not `http://`, not `javascript:`), or the request fails with `400`.
- `actor_id` must come from the authenticated user in the calling service, never from user-typed input

### Get a user's inbox (called by the dashboard)

`GET /users/<user_id>/notifications?unread=true&page=1&per_page=20`

```json
{
  "items": [ { "id": "...", "type": "request_canceled", "...": "..." } ],
  "total": 42,
  "page": 1,
  "per_page": 20,
  "has_next": true
}
```

### Unread count (for the bell badge)

`GET /users/<user_id>/notifications/unread-count`

```json
{ "unread_count": 3 }
```

### Mark one as read

`POST /notifications/<notification_id>/read` with body `{"user_id": "..."}`

Returns `200` if it was marked, `404` if it does not exist, is not this user's, or is already read.

### Mark all as read

`POST /users/<user_id>/notifications/read-all`

```json
{ "marked": 3 }
```

## Auth

- Service-to-service calls use a shared API key in a request header (header name and key distribution to be agreed with the other services).
- The dashboard passes the logged-in user's ID. The user can only read and mark their own notifications
- Never expose this service directly to browsers. The dashboard backend calls it on the user's behalf.

---

## How to integrate (for other services)

1. Work out the recipients and the actor in your own service.
2. Pick a `type` from the enum. If none fits, ask for a new one to be added.
3. Build a `link` as a relative path to the page where the user should land.
4. Call `POST /notifications` as shown above.

Quick test:

```bash
curl -X POST http://localhost:5001/notifications \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <key>" \
  -d '{"recipient_ids":["tutor_7"],"type":"booking_created","actor_id":"student_42","title":"New booking","link":"/bookings/1"}'
```
